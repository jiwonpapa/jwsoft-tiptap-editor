# RC1 실제 기능 감사 — 2026-08-31

## 판정: 제품 완료 불가

실제 G7 사용자 화면에서 공개 이미지 업로드, 빈 본문 저장 차단, 저장된 동영상의 플레이어 출력이 실패했습니다. 기존 자동 검사 통과를 전체 사용자 기능 정상으로 보고한 판단은 철회합니다. **전 기능 정상 확인을 완료한 보고서가 아닙니다.** 아래 미검증 항목은 완료로 계산하지 않습니다.

이번 작업은 검증·원인 조사입니다. 제품 코드 수정, 커밋, 신규 패키징, 재배포는 하지 않았습니다. 공유 개발 환경이나 다른 제품 작업을 사용하지 않았습니다.

- 실제 브라우저에서 파일 선택, 클립보드 붙여넣기, 설정 저장, 글 등록, 재조회 및 수정 화면 진입을 실행했습니다. 업로드 응답이나 게시글 저장을 모의 응답으로 바꾸지 않았습니다.

## 확정된 실패와 원인

### F01. 공개 게시판 이미지 모달에 파일 선택 UI가 없음 — 실패

재현: 공개 게시판 글쓰기 → 이미지 → 파일 업로드. 파일 선택 영역이 비고, 이미지 삽입을 누르면 먼저 이미지를 선택하라는 안내만 나옵니다.

- 브라우저 오류: `TypeError: l.map is not a function`, `onFilesChange`.
- 공개 Basic FileUploader는 `{ target: { value: files, files } }` 이벤트 객체를 전달합니다.
- [filePicker.ts](../../resources/js/g7/filePicker.ts)는 배열을 전제로 `pending.map(...)`을 호출합니다.
- [imageUploadQueue.ts](../../resources/js/editor/imageUploadQueue.ts)는 실제 렌더 성공을 기다리지 않고 대체 파일 선택기를 숨깁니다. 이후 React 오류가 발생해도 대체 UI가 복구되지 않습니다.
- Admin Basic은 배열을 전달하므로 관리자 파일 선택·실업로드·편집기 삽입은 성공했습니다. **모든 화면에서 이미지 업로드가 실패하는 것은 아닙니다.** 관리자 삽입 후 글 저장은 이번 사례에서 실행하지 않았습니다.
- 기존 [filePicker.test.ts](../../resources/js/g7/filePicker.test.ts)는 가짜 컴포넌트와 배열 콜백만 검사하여 공개 템플릿의 실제 입력 계약을 놓쳤습니다.

증거: `.build/feature-audit-20260831/image-empty-modal.png`, 공개/관리자 콘솔·DOM 관찰, 신규 이미지 레코드 ID 2·3.

### F02. 제목만 입력한 빈 본문이 저장됨 — 실패

재현: 공개 자유게시판 글쓰기 → 제목만 입력 → 본문을 건드리지 않고 등록.

- 실제 게시글 ID **221** 생성, DB 본문 **`<p></p>`**.
- 빈 편집기 HTML을 의미상 빈 값으로 처리하지 않습니다.
- [CanonicalizeEditorHtml.php](../../src/Http/Middleware/CanonicalizeEditorHtml.php)는 HTML 정책을 정제하지만 의미 있는 본문 존재 여부는 검사하지 않습니다. 게시판 문자열 필수/길이 검사만으로는 빈 HTML을 차단하지 못하는 경우가 있습니다.
- 이번 확정 재현은 해당 공개 게시판입니다. 관리자·답글·다국어의 모든 빈 값 조합이 같다고 단정하지 않습니다.
- 정상 이미지 전용 글 ID **228**, MP4 전용 글 ID **223**도 저장됐습니다. 수정 시 이 정상 미디어 본문까지 빈 글로 막으면 안 됩니다.

증거: `.build/feature-audit-20260831/after.json`의 `newPosts`.

### F03. 업로드·삽입한 영상이 게시글에서 플레이어가 되지 않음 — 실패

재현: 영상 기능과 파일 업로드 ON → 실제 MP4 선택 → 동영상 삽입 → 글 등록 → 글 보기.

- H.264/AAC, 12초, 1,235,246바이트의 정상 MP4 사용. 업로드·서버 파일 저장은 성공했습니다.
- 게시글 **223**은 어두운 `MP4 video` 링크 박스만 표시합니다. 공개 새로고침과 관리자 조회에서도 플레이어가 없습니다.
- YouTube 자동 삽입 게시글 **225**, Vimeo 수동 삽입 게시글 **226**도 플레이어 대신 링크가 남습니다.
- 파일 제공 URL을 직접 열면 `duration=12`, `currentTime=12`, `ended=true`, `readyState=4`, `videoWidth=640`, `error=null`을 확인했습니다. **파일 디코딩 성공과 게시글 플레이어 실패를 구분합니다.**
- [mediaRenderer.ts](../../resources/js/editor/mediaRenderer.ts)는 정해진 figure를 런타임 플레이어로 바꾸지만, [injectContentStyles.ts](../../resources/js/handlers/injectContentStyles.ts)는 onMount의 단일 microtask에서만 실행됩니다. 비동기 본문 표시/재렌더 뒤 재실행 경로가 없는 것이 유력 원인입니다. 정확한 호출 타이밍은 추가 계측이 필요합니다.
- 기존 [editor-ui.spec.ts](../../tests/e2e/editor-ui.spec.ts)의 MP4 검사는 모의 청크 응답과 짧은 가짜 MP4 데이터로 canonical 노드만 검사합니다. 실제 G7 저장 후 재생 검사가 아니었습니다.

증거: `mp4-no-player.png`, `youtube-no-player.png`, `after.json`.

### F04. 영상 진행률과 파일명 표시 — UX 실패 / 저장 사실 구분

- 실제 파일 하나에서 **동영상 청크 0/2 업로드 중…** 표시를 재현했습니다. 분모는 파일 개수가 아니라 청크 수입니다. 파일 진행률로 알아보기 어렵습니다.
- 서버 `original_name`에는 원래 `.mp4` 이름이, 저장 경로에도 `.mp4` 확장자가 보존됩니다. 확장자 없는 공개 제공 URL 자체가 파일 손실 증거는 아닙니다.
- 삽입 노드 표시 이름은 원래 파일명이 아닌 `MP4 video`로 바뀝니다. 원래 이름을 사용자에게 유지하는 UX는 충족하지 못합니다.
- Range `bytes=0-1023` 요청에 `206`이 아닌 전체 파일 `200` 응답을 받았습니다. 이것을 이번 링크 박스의 원인으로 단정하지 않습니다. 실제 플레이어 탐색 검증도 남아 있습니다.

### F05. URL 자동 변환과 SNS 실제 지원 범위 — 부분 성공 / 요구 불충족

- 기능 ON에서 빈 문단에 YouTube URL을 붙여넣으면 미디어 노드가 생깁니다. 직접 입력 후 Enter는 일반 링크로 남습니다.
- 사용자 제공 X URL을 빈 편집기에 붙여넣으면 실제 제목·설명 카드가 생성되고 게시글 **224**에 저장·출력됩니다.
- 현재 SNS 구현은 제목·설명의 **링크 카드**이며 게시물 전체, SNS 자체 영상 플레이어/상호작용을 표시하는 임베드가 아닙니다.
- [createEditor.ts](../../resources/js/editor/createEditor.ts)의 자동 변환 조건은 빈 문단·단일 URL 붙여넣기로 제한됩니다.
- [LinkPreviewService.php](../../src/Services/LinkPreviewService.php)는 일부 SNS 응답 실패를 제공자 이름만 있는 카드로 돌려줍니다. Facebook 이름만 있는 카드가 생길 수 있는 코드 경로는 확인했으나, 사용자가 올린 Facebook 원본 URL의 실제 재현은 하지 않았습니다.
- Instagram·TikTok·Facebook·Threads의 실제 게시물별 성공을 이번 X 성공으로 대신하지 않습니다.

## 수정 후 반드시 다시 확인할 순서

1. 실패 재현을 먼저 회귀 테스트로 고정: Basic 이벤트 객체와 Admin 배열 양쪽, 빈 HTML/공백/입력 후 전부 삭제, 실제 G7 비동기 본문 출력.
2. 코드 수정 후 정적·단위·PHP·통합 검사. 테스트의 기대값을 낮춰 통과시키지 않습니다.
3. 실제 G7 공개/관리자에서 파일 선택→업로드→삽입→등록→재조회→재편집. 정상 이미지·동영상 전용 글과 빈 글 차단을 함께 확인합니다.
4. 실제 재생 가능한 MP4로 플레이어 생성, 재생 시간 증가, 탐색, 전체화면 확인. YouTube/Vimeo는 실제 게시글 화면에서 로드·실패 안내까지 확인합니다.
5. SNS는 제공자·입력 방식·설정 ON/OFF·성공/차단/실패를 각각 기록하고, 링크 카드와 실제 임베드를 구분합니다.
6. 미검증 편집 도구·6종 대상 화면·반응형/실기기·권한·수명주기를 닫은 후 동일 ZIP의 staging 검증. 이후 승인된 운영 배포와 배포 후 실제 핵심 흐름을 별도 확인합니다.

이 순서를 새 자동 배포 gate에 강제하는 구현은 아직 하지 않았습니다. 현재 문서는 실제 실패 판정과 후속 검증 조건이지 수정·배포 완료 증거가 아닙니다.
