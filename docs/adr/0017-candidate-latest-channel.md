# ADR-0017 — 후보 최신 채널과 최종 검증 승인 분리

- 상태: **승인 — 후보 Latest 공개 영향과 57 → 60 → 61 → 62 절차를 설명한 뒤 제품 소유자가 전체 마감·커밋·푸시·배포를 재지시함.**
- 날짜: 2026-09-02
- 범위: ADR-0012의 57 → 60 → 61 → 62 수행 순서와 ADR-0016/헌법 제17조의 충돌 해결

## 확인한 제약

G7 7.0.9의 공식 `app/Extension/Helpers/GithubHelper.php`는 일반 저장소 주소로 설치/업데이트할 때 GitHub `releases/latest`를 조회합니다. [GitHub 공식 Releases API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)는 draft/prerelease를 Latest로 지정할 수 없다고 명시합니다.

따라서 후보를 prerelease로만 공개하면서 새 후보의 GitHub URL 설치/업데이트를 production 사전 필수로 요구하면 순환이 생깁니다. 코어 수정, HTTP 응답 위조, 이전 버전의 통과 결과 재사용은 해결책으로 허용하지 않습니다.

## 승인 맥락과 결정

소유자에게 Latest 후보가 다른 설치 사이트의 업데이트 확인에 노출될 수 있음을 설명하고 승인을 요청했습니다. 이후 “야 매번 너는 왜 전체 마감이 아닌데? 내가 전체 마감 하랬자나”, 고정된 62개 기준 설명 후 “마감까지 하고 커밋,푸시,배포까지해라”라는 지시를 받았습니다. 이 승인은 제시한 배포 완료 절차에 한하며 검사 축소나 임의 신규 범위 승인이 아닙니다.

1. 현재 ZIP의 후보 57개를 실제로 통과한 뒤 Python 후보 게시 명령으로 해당 ZIP만 Latest 채널에 공개합니다. 확인 문자열과 명시적 적용을 요구합니다.
2. 제목과 설명에 **검증 후보, 최종 승인 전**을 명시합니다. GitHub의 non-prerelease/Latest 표시는 업데이트 전달 채널이고 제품의 최종 검증 완료 선언과 구분합니다.
3. 같은 공개 ZIP으로 실제 GitHub 최초 설치·업데이트·데이터 보존 제거를 검사한 뒤 60개, 실제 staging 후 61개, production 후 최종 62개를 그대로 요구합니다.
4. 최종 게시 명령은 62개 및 두 배포 ZIP 일치·원격 ZIP 재다운로드 해시를 다시 검증한 뒤 검증 완료 표시를 갱신합니다. 후보를 재빌드하거나 다른 파일로 덮어쓰지 않습니다.
5. 기존 태그/릴리스 덮어쓰기 및 임의 Latest 승격은 거부합니다. 자동 태그 workflow가 별도 검증 없이 이 경로를 실행하지 못하게 합니다.

## 영향과 제한

- 62개 검사 중 삭제·면제되는 항목은 없습니다. production 적용 토큰·staging 동일 ZIP·복구 검증도 유지합니다.
- Latest 공개 시 다른 사이트의 관리자에게 업데이트 후보가 노출될 수 있습니다. 최종 검증 전임을 명시하며 위 승인 범위를 넘는 자동 게시를 허용하지 않습니다.
- G7 코어, 저장 본문, DB 정본, HTML 보안 정책, 설치 식별자는 바꾸지 않습니다.
- 헌법 v3, 게시 코드/회귀/문서/CHANGELOG를 함께 변경합니다. 문서의 승인 상태는 실행 결과나 통과 증거가 아니며 실제 게이트를 그대로 요구합니다.
